# API Deviations

CoilPro's technical specification (`doc/11 SDK – Technische Spezifikation.md`) describes endpoints, scopes, and protocol details as they were understood at planning time. Tesla changes the Fleet API's hosts, scopes, and payloads without much notice, so every endpoint, scope, and protocol detail is re-verified against [developer.tesla.com](https://developer.tesla.com) (and, for the Vehicle Command Protocol, [`teslamotors/vehicle-command`](https://github.com/teslamotors/vehicle-command)) before it ships in code.

This document is the record of what changed: whenever verification turns up a difference between what the spec assumed and what the real API actually requires, it gets logged here — with a link back to the source that confirmed it. Treat it as the changelog between "what we planned" and "what we shipped," and check it before trusting a hostname, scope name, or field from the spec doc at face value.

## Deviations

| Date | Area | Spec said | Actual | Source |
|---|---|---|---|---|
| 2026-07-09 | `vehicle_data` `endpoints` param | Not specified in the planning-time spec | CoilPro's `VehicleDataEndpoint.ToQueryValue()` joins selected segments with `;` (e.g. `charge_state;drive_state`) as the `endpoints` query parameter | **Confirmed live 2026-11-24:** `;` is right. A comma-separated value (`charge_state,drive_state`) is accepted with `200` but **silently returns none of the requested sub-states** — no error, just missing data. Also confirmed: `drive_state` contains `latitude`/`longitude` only when `location_data` is requested too (`drive_state;location_data`), and the token needs the `vehicle_location` scope |
| 2026-07-09 | Charging-history endpoint path | Not specified in the planning-time spec | Assumed `api/1/dx/charging/history`; response modeled as `ChargingHistoryPage` (`data`, `totalResults`, `hasMoreData`) with per-record fields `vin`, `chargeStartDateTime`, `chargeStopDateTime`, `siteLocationName` | **Confirmed live 2026-11-24, with corrections:** path is right, but the response has **no `{ "response": ... }` envelope** — it is `{ "data": [...], "totalResults": n }` at the top level, and `hasMoreData` is absent. CoilPro unwrapped the envelope and therefore returned an empty page every time; fixed (`FleetApiExecutor` `unwrapEnvelope: false`). Records also carry `sessionId`, `unlatchDateTime`, `countryCode`, `billingType`, `vehicleMakeType`, `fees[]` (per fee: `feeType` e.g. `CHARGING`/`CONGESTION`, `currencyCode`, `uom` `kwh`/`min`, base/tier rates, usages and totals, `totalDue`, `netDue`, `isPaid`, `status`) and `invoices[]` (`fileName`, `contentId`, `invoiceType`); now modeled |
| 2026-07-09 | Rate-limit header names | Not specified in the planning-time spec | `RateLimitInfo.FromHeaders` reads `x-ratelimit-limit` / `x-ratelimit-remaining` / `x-ratelimit-reset` (plus the standard `Retry-After`) | **Wrong — confirmed live 2026-11-24:** Tesla sends one triple per bucket: `ratelimit-<bucket>-limit` / `-remaining` / `-reset`, e.g. `ratelimit-device-data-per-vehicle-limit: 60`, `-remaining: 58`, `-reset: 5`. No `x-` prefix, and `reset` is **seconds until reset**, not a Unix timestamp. `LastRateLimit` was therefore always null. Fixed: `RateLimitInfo.FromHeaders` reads any `(x-)ratelimit-[<bucket>-](limit\|remaining\|reset)`, exposes the bucket as `Category`, picks the bucket with the fewest remaining, and treats `reset` < 1e9 as relative seconds |
| 2026-07-09 | Fleet API error body shape | Not specified in the planning-time spec | `TeslaApiException` parsing assumes `{ "error": "...", "error_description": "..." }` | **Confirmed 2026-07-28**, with an addition: the real shape is `{ "response": null, "error": "...", "error_description": "...", "txid": "..." }`. `error_description` is frequently empty, so `error` carries the useful text — `TryParseErrorCode` already prefers it. `txid` is Tesla's correlation id; not modeled, but preserved in `TeslaApiException.ResponseBody` and worth quoting in support requests. Source: [teslamotors/vehicle-command#250](https://github.com/teslamotors/vehicle-command/issues/250), [#104](https://github.com/teslamotors/vehicle-command/issues/104) |
| 2026-07-28 | Partner registration is **per region** | Not specified in the planning-time spec | Registering against the EU host does *not* register against the NA host. Calls into an unregistered region fail with region errors *even when the region is otherwise correct* — a misleading symptom. `coilpro partner register` therefore prints a reminder naming the other region. Source: [teslamotors/vehicle-command#104](https://github.com/teslamotors/vehicle-command/issues/104) (Tesla contributor) |
| 2026-07-28 | `partner_accounts/public_key` parameter passing | Not specified in the planning-time spec | `domain` travels as a **query parameter on a GET**, not in a request body. Sending it as a body returns 404 and omitting it returns `param is missing or the value is empty: domain`. Pinned by a test in `TeslaPartnerClientTests`. Source: [teslamotors/vehicle-command#104](https://github.com/teslamotors/vehicle-command/issues/104) |
| 2026-07-28 | Command key curve | Spec says "EC P-256 (NIST)" — correct | **Confirmed**: `secp256r1` / `prime256v1`, PEM-encoded, at `https://<domain>/.well-known/appspecific/com.tesla.3p.public-key.pem`. Note the trap: Tesla's own `vehicle-command` README uses **secp384r1** in its `openssl req` example — that key is for the HTTP proxy's *TLS certificate*, not for command signing. `TeslaKeyPair.FromPrivateKeyPem` rejects non-P-256 keys for exactly this reason. Source: [developer.tesla.com partner endpoints](https://developer.tesla.com/docs/fleet-api/endpoints/partner-endpoints), [vehicle-command README](https://github.com/teslamotors/vehicle-command) |
| 2026-07-28 | Public-key PEM byte format | Not specified in the planning-time spec | SubjectPublicKeyInfo (`-----BEGIN PUBLIC KEY-----`) **with a trailing LF**. .NET's `ExportSubjectPublicKeyInfoPem()` omits that newline while `openssl ec -pubout` and Go's `encoding/pem` (Tesla's own tooling) emit it, so `TeslaKeyPair` appends it. Verified byte-identical against `openssl pkey -pubout` |
| 2026-07-28 | Registered public key is returned as hex | Not specified in the planning-time spec | `GET partner_accounts/public_key` echoes the key as a **hex-encoded uncompressed EC point** (`04` + X + Y, 130 hex chars), not as PEM. `TeslaKeyPair.ExportPublicKeyHex()` produces the comparable form; `coilpro partner public-key` diffs the two |
| 2026-11-24 | Vehicle Command Protocol (M3 planning) | Spec §4: HMAC-SHA256 over the serialized message with the session key; invalidate session cache on `SIGNED_MESSAGE_FAULT`; `POST /vehicles/{id}/signed_command` with a "Base64 envelope" | **Partly wrong / outdated** (research against `vehicle-command@0a582da`, details in [`m3-command-protocol.md`](./m3-command-protocol.md)): Infotainment uses `AES_GCM_DETACHED` when the car advertises it, only VCSEC uses HMAC; the HMAC key is `HMAC(K,"authenticated command")` with `K = SHA1(ECDH x)[:16]`, over `metadata TLVs ‖ 0xFF ‖ payload`; replies are AES-GCM-encrypted (fw ≥ 2024.38) and must be decrypted; on retryable faults the client adopts the authenticated session info from the fault reply and re-signs — no session reset; path takes the **VIN**; body `{"routable_message":"<b64>"}` → `{"response":"<b64>"}`, and HTTP 200 does not mean success; generic 5xx retries are unsafe (command may have executed) |
| 2026-11-24 | `dx/*` endpoints have no envelope | Docs examples show `{ "response": ... }` | **Confirmed live:** `dx/vehicles/options` (`{codes:[…]}`), `dx/warranty/details`, `dx/vehicles/subscriptions/eligibility`, `dx/vehicles/upgrades/eligibility` answer **bare** JSON, like `dx/charging/history`. CoilPro parses all `dx/*` endpoints tolerantly (envelope or bare). `upgrades` pricing also carries `includesTax` |
| 2026-11-24 | `recent_alerts` shape | Docs: `time` ISO 8601, field `audience` | **Live:** `time` is RFC 1123 (`Tue, 24 Nov 2026 09:27:27 +0000`) and the list field is **`audiences`**. `VehicleAlert.Time` is the raw string; `TimeUtc` parses it |
| 2026-11-24 | Vehicle REST endpoints, first live run | — | **Confirmed live (vehicle offline):** `vehicles` (page + single), `vehicle_data_cached` (works offline; no top-level vehicle fields, only `charge_state`/`climate_state`/`gui_settings`/`vehicle_state`), `fleet_status`, `recent_alerts`, `release_notes` (flat, not double-nested), `service_data`, `service_history` + visit detail, `drivers`, `invitations`, `fleet_telemetry_config` (`config: null` when none), `fleet_telemetry_errors`, `users/me`, `users/orders`, `users/region`, `dx/charging/history` with `pageSize`, `dx/charging/invoice/{contentId}` (**PDF**, `%PDF-`), `/status` (`ok`), `products` (incl. Wall Connector sites: `resource_type: wall_connector`, `components.wall_connectors[]`). `mobile_enabled` answers **408 "vehicle unavailable"** while the vehicle is offline — it needs an online vehicle. Energy endpoints answer **403 "Unauthorized missing scopes"** without `energy_device_data` in the user token |
| 2026-11-24 | Signed commands, first live run | — | **Confirmed live** (EU Model Y, fw 2026.38.6) with the native C# implementation: `flash` (Infotainment, with `--wake`) → executed; `charge-limit 80` at limit 80 → `CarServer` refusal `already_set`, surfaced as `CommandResult`; `unlock` then `lock` (VCSEC, HMAC_PERSONALIZED) → both executed, `vehicle_state.locked = true` afterwards. Handshake, signing, response decryption and reply interpretation work on both domains. Observed with `--debug`: Infotainment advertises detached AES-GCM and is signed with it, VCSEC uses HMAC; both domains echo `request_uuid` and encrypt their replies. Not yet observed: encrypted fault replies (no fault occurred) |
| 2026-11-24 | `fleet_status` | Not specified in the planning-time spec | **Confirmed live:** `POST api/1/vehicles/fleet_status` with `{"vins":[…]}` returns `key_paired_vins`, `unpaired_vins` and per VIN `firmware_version`, `vehicle_command_protocol_required`, `fleet_telemetry_version`, `total_number_of_keys`, `discounted_device_data`. Model Y: fw `2026.38.6`, protocol required, key paired. Usable as a cheap "is the virtual key installed?" check |
| 2026-11-24 | Client-credentials `audience` value | Spec: "audience = Fleet API host of the region" | **Confirmed live:** the value must be the bare origin, e.g. `https://fleet-api.prd.eu.vn.cloud.tesla.com` — **no trailing slash**. CoilPro sent `Uri.ToString()`, which appends `/`, and the token endpoint answered `400 {"error":"invalid_audience","error_description":"The 'audience' parameter is invalid. Include valid audience in the request."}`. Fixed in `TeslaAuthClient` (`GetLeftPart(UriPartial.Authority)`); a test now pins the literal string per region. Source: live run of `coilpro partner register --region eu` |
| 2026-11-24 | Registration error for a non-allowed origin | Not specified in the planning-time spec | **Confirmed live:** `POST partner_accounts` answers `412 Precondition Failed` with the message `Root domain <root> must match registered allowed origin on https://developer.tesla.com/dashboard/app-details/<app-id>`. The check runs against the root domain (`dotnetservices.de` for `coil.dotnetservices.de`), consistent with the row below. Source: live run of `coilpro partner register --region eu` |
| 2026-11-24 | Partner-token scopes | Not specified in the planning-time spec | **Confirmed live:** a client-credentials token requested with only `openid offline_access` (the `TeslaAuthOptions` default, meant for the authorization-code flow) can register (`POST partner_accounts` succeeded), but `GET partner_accounts/public_key` answers `403 Unauthorized missing scopes`. Requesting `openid vehicle_device_data vehicle_cmds vehicle_charging_cmds` (Tesla's partner-token example) fixes it. The CLI's partner commands now request that set. Library consumers of `TeslaPartnerClient` must set `TeslaAuthOptions.Scopes` the same way. Source: live run of `coilpro partner public-key --region eu` |
| 2026-11-24 | Partner registration, EU | — | **Done live:** `coil.dotnetservices.de` registered in EU (account id `e0953cc0-…`); `GET partner_accounts/public_key` echoes the hex point of the local key exactly. NA not registered |
| 2026-11-24 | Authorize host ≠ token host | Spec: one auth host `fleet-auth.prd.vn.cloud.tesla.com` | **Confirmed live + docs:** the interactive authorize page is `https://auth.tesla.com/oauth2/v3/authorize`; only `/oauth2/v3/token` (code exchange, refresh, client credentials) lives on `fleet-auth.prd.vn.cloud.tesla.com`. Sending the user to `fleet-auth…/authorize` fails with "The 'redirect_uri' supplied is not registered for this 'client_id'" even when the redirect URI is registered. New `TeslaEndpoints.AuthorizeBaseUrl` (default `https://auth.tesla.com`). Source: [third-party tokens](https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens), live `coilpro login` |
| 2026-11-24 | Code exchange needs `audience` | Not specified in the planning-time spec | Tesla's docs list `audience` (Fleet API base URL, bare origin) as **required** for `grant_type=authorization_code`, next to `client_secret`. CoilPro did not send it; now it does. Source: [third-party tokens](https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens) |
| 2026-11-24 | Redirect URI host | RFC 8252 prefers `127.0.0.1` for loopback redirects | developer.tesla.com only accepts `localhost` redirect URIs. `coilpro login` uses `http://localhost:<port>/callback`. Source: Tesla developer dashboard |
| 2026-07-28 | Registration domain constraint | Not specified in the planning-time spec | The domain must match the **root domain of an `allowed_origin`** configured on developer.tesla.com (e.g. `123.abc.com` is accepted for an allowed origin of `www.abc.com`), and must be a bare host — no scheme, no path. `TeslaPartnerClient.NormalizeDomain` enforces the bare-host part locally. Source: [developer.tesla.com partner endpoints](https://developer.tesla.com/docs/fleet-api/endpoints/partner-endpoints) |
