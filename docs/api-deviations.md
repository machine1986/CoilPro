# API Deviations

Coil.NET's technical specification (`doc/11 SDK – Technische Spezifikation.md`) describes endpoints, scopes, and protocol details as they were understood at planning time. Tesla changes the Fleet API's hosts, scopes, and payloads without much notice, so every endpoint, scope, and protocol detail is re-verified against [developer.tesla.com](https://developer.tesla.com) (and, for the Vehicle Command Protocol, [`teslamotors/vehicle-command`](https://github.com/teslamotors/vehicle-command)) before it ships in code.

This document is the record of what changed: whenever verification turns up a difference between what the spec assumed and what the real API actually requires, it gets logged here — with a link back to the source that confirmed it. Treat it as the changelog between "what we planned" and "what we shipped," and check it before trusting a hostname, scope name, or field from the spec doc at face value.

## Deviations

| Date | Area | Spec said | Actual | Source |
|---|---|---|---|---|
| 2026-07-09 | `vehicle_data` `endpoints` param | Not specified in the planning-time spec | Coil.NET's `VehicleDataEndpoint.ToQueryValue()` joins selected segments with `;` (e.g. `charge_state;drive_state`) as the `endpoints` query parameter | Status: to verify — [developer.tesla.com](https://developer.tesla.com) `vehicle_data` reference |
| 2026-07-09 | Charging-history endpoint path | Not specified in the planning-time spec | Assumed `api/1/dx/charging/history`; response modeled as `ChargingHistoryPage` (`data`, `totalResults`, `hasMoreData`) with per-record fields `vin`, `chargeStartDateTime`, `chargeStopDateTime`, `siteLocationName` | Status: to verify — path and shape are provisional, not confirmed against a live account |
| 2026-07-09 | Rate-limit header names | Not specified in the planning-time spec | `RateLimitInfo.FromHeaders` reads `x-ratelimit-limit` / `x-ratelimit-remaining` / `x-ratelimit-reset` (plus the standard `Retry-After`) | Status: to verify — Fleet API rate-limit header contract is not fully public |
| 2026-07-09 | Fleet API error body shape | Not specified in the planning-time spec | `TeslaApiException` parsing assumes `{ "error": "...", "error_description": "..." }` | **Confirmed 2026-07-28**, with an addition: the real shape is `{ "response": null, "error": "...", "error_description": "...", "txid": "..." }`. `error_description` is frequently empty, so `error` carries the useful text — `TryParseErrorCode` already prefers it. `txid` is Tesla's correlation id; not modeled, but preserved in `TeslaApiException.ResponseBody` and worth quoting in support requests. Source: [teslamotors/vehicle-command#250](https://github.com/teslamotors/vehicle-command/issues/250), [#104](https://github.com/teslamotors/vehicle-command/issues/104) |
| 2026-07-28 | Partner registration is **per region** | Not specified in the planning-time spec | Registering against the EU host does *not* register against the NA host. Calls into an unregistered region fail with region errors *even when the region is otherwise correct* — a misleading symptom. `coil partner register` therefore prints a reminder naming the other region. Source: [teslamotors/vehicle-command#104](https://github.com/teslamotors/vehicle-command/issues/104) (Tesla contributor) |
| 2026-07-28 | `partner_accounts/public_key` parameter passing | Not specified in the planning-time spec | `domain` travels as a **query parameter on a GET**, not in a request body. Sending it as a body returns 404 and omitting it returns `param is missing or the value is empty: domain`. Pinned by a test in `TeslaPartnerClientTests`. Source: [teslamotors/vehicle-command#104](https://github.com/teslamotors/vehicle-command/issues/104) |
| 2026-07-28 | Command key curve | Spec says "EC P-256 (NIST)" — correct | **Confirmed**: `secp256r1` / `prime256v1`, PEM-encoded, at `https://<domain>/.well-known/appspecific/com.tesla.3p.public-key.pem`. Note the trap: Tesla's own `vehicle-command` README uses **secp384r1** in its `openssl req` example — that key is for the HTTP proxy's *TLS certificate*, not for command signing. `TeslaKeyPair.FromPrivateKeyPem` rejects non-P-256 keys for exactly this reason. Source: [developer.tesla.com partner endpoints](https://developer.tesla.com/docs/fleet-api/endpoints/partner-endpoints), [vehicle-command README](https://github.com/teslamotors/vehicle-command) |
| 2026-07-28 | Public-key PEM byte format | Not specified in the planning-time spec | SubjectPublicKeyInfo (`-----BEGIN PUBLIC KEY-----`) **with a trailing LF**. .NET's `ExportSubjectPublicKeyInfoPem()` omits that newline while `openssl ec -pubout` and Go's `encoding/pem` (Tesla's own tooling) emit it, so `TeslaKeyPair` appends it. Verified byte-identical against `openssl pkey -pubout` |
| 2026-07-28 | Registered public key is returned as hex | Not specified in the planning-time spec | `GET partner_accounts/public_key` echoes the key as a **hex-encoded uncompressed EC point** (`04` + X + Y, 130 hex chars), not as PEM. `TeslaKeyPair.ExportPublicKeyHex()` produces the comparable form; `coil partner public-key` diffs the two |
| 2026-11-24 | Client-credentials `audience` value | Spec: "audience = Fleet API host of the region" | **Confirmed live:** the value must be the bare origin, e.g. `https://fleet-api.prd.eu.vn.cloud.tesla.com` — **no trailing slash**. Coil.NET sent `Uri.ToString()`, which appends `/`, and the token endpoint answered `400 {"error":"invalid_audience","error_description":"The 'audience' parameter is invalid. Include valid audience in the request."}`. Fixed in `TeslaAuthClient` (`GetLeftPart(UriPartial.Authority)`); a test now pins the literal string per region. Source: live run of `coil partner register --region eu` |
| 2026-11-24 | Registration error for a non-allowed origin | Not specified in the planning-time spec | **Confirmed live:** `POST partner_accounts` answers `412 Precondition Failed` with the message `Root domain <root> must match registered allowed origin on https://developer.tesla.com/dashboard/app-details/<app-id>`. The check runs against the root domain (`dotnetservices.de` for `coil.dotnetservices.de`), consistent with the row below. Source: live run of `coil partner register --region eu` |
| 2026-11-24 | Partner-token scopes | Not specified in the planning-time spec | **Confirmed live:** a client-credentials token requested with only `openid offline_access` (the `TeslaAuthOptions` default, meant for the authorization-code flow) can register (`POST partner_accounts` succeeded), but `GET partner_accounts/public_key` answers `403 Unauthorized missing scopes`. Requesting `openid vehicle_device_data vehicle_cmds vehicle_charging_cmds` (Tesla's partner-token example) fixes it. The CLI's partner commands now request that set. Library consumers of `TeslaPartnerClient` must set `TeslaAuthOptions.Scopes` the same way. Source: live run of `coil partner public-key --region eu` |
| 2026-11-24 | Partner registration, EU | — | **Done live:** `coil.dotnetservices.de` registered in EU (account id `e0953cc0-…`); `GET partner_accounts/public_key` echoes the hex point of the local key exactly. NA not registered |
| 2026-07-28 | Registration domain constraint | Not specified in the planning-time spec | The domain must match the **root domain of an `allowed_origin`** configured on developer.tesla.com (e.g. `123.abc.com` is accepted for an allowed origin of `www.abc.com`), and must be a bare host — no scheme, no path. `TeslaPartnerClient.NormalizeDomain` enforces the bare-host part locally. Source: [developer.tesla.com partner endpoints](https://developer.tesla.com/docs/fleet-api/endpoints/partner-endpoints) |
